Module C_syntax.Param_guards

Builtin parameter guards (gh-ocannl-1768): a check that every builtin call a kernel makes passes each argument at a type the parameter holds without narrowing, enabled by the test seam Param_guards.with_guards.

A builtin's parameter type and the C type of the operand its call site passes were never compared: the call converts implicitly, and a conversion that changes the value rather than the representation is silent. That is how half reached half_to_uint4x32 by VALUE on cc and Metal (gh-ocannl-1704: 1.5 became counter 1), while every test of the table fed it raw bits on both sides. Under the seam each function a kernel calls is shadowed, after every definition and before the kernel, by a function-like macro that passes each argument through a guard naming the parameter type read off the function's own definition. The guard is the C++ narrowing rule -- the one MSL's own compiler applies to a braced initialization: floating to integer, integer to floating, a narrower floating type, or an integer type whose range does not hold the operand's all fail, while a type the parameter holds exactly (a promotion, a wider type) passes. In C it is a _Static_assert over __typeof__ of the argument, which evaluates the argument once, and in the C++ dialects the braced initialization itself. A failing guard fails the kernel's compile, which is what test/operations/op_table_compile claims never happens to an in-domain arm.

A definition the guard cannot read is left unguarded, with the reason parameter_types gives: a macro (no parameter types), a template or an overload set (the compiler picks the parameter type per call), a definition with no function, or a parameter passed by pointer, reference or array.

val parameter_types : key:Base.string -> Base.string -> (Base.string Base.list, Base.string) Base.Result.t

The parameter types of the function key that a table entry's definition defines, read off its signature, or why there are none to guard: a_macro and not_a_function for an entry that is no function, another reason for a function the guard skips.

val a_macro : Base.string

The reason given for a macro.

val not_a_function : Base.string

The reason given for an entry that names key nowhere as a call or a definition: a type, a constant, a header.

val prelude : param_guard_dialect -> Base.string

The helpers the guards of guard expand to, emitted once before them.

val guard : param_guard_dialect -> key:Base.string -> Base.string Base.list -> Base.string

The macro shadowing key, whose parameters have these types.

val with_guards : ?guard:Base.bool -> ?overrides:(Base.string * Base.string) Base.list -> (Base.unit -> 'a) -> 'a

with_guards ?guard ?overrides f runs f with every kernel prelude of a backend that declares a param_guard_dialect guarding the functions the kernel calls (unless guard is false), and with each (key, definition) of overrides replacing that key's definition in the backend's table -- how a test plants a defect, and shows both that it compiles unguarded and that the guards catch it. A test seam: kernels are never guarded outside it. An override naming a key the table lacks fails the prelude's assembly.

val active : Base.unit -> (Base.bool * (Base.string * Base.string) Base.list) Base.option

Some (guard, overrides) inside with_guards, None outside it.

val note_emitted : Base.int -> Base.unit
val emitted : Base.unit -> Base.int

How many guards the preludes assembled in this process carried: zero where no backend declares a dialect, which is how a test sees that its guards were never emitted.
